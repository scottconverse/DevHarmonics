An AI agent makes the change. The gates decide if it ships.

DevHarmonics runs any qualified model — over three interchangeable lanes — to make one bounded change to a git repository on your own machine. Every attempt leaves an append-only receipt, and nothing merges or leaves your machine without you.

The problem

An AI agent can rewrite your repository faster than you can check it.

Hand a coding agent a task and it edits files, runs commands, and reports success. What it doesn't give you is a boundary — a place where the change is verified before it counts, evidence of what actually happened, and independence from the one vendor's app you happened to be using. When "the model said it's done" is the only signal, a confident wrong answer looks exactly like a correct one.

Instead of trust

Evidence

Every attempt — success, refusal, or a run that never started — writes an append-only receipt first. A run that leaves no evidence is treated as one that never happened.

Instead of lock-in

Three lanes

Subscription CLIs, local model servers, and ACP adapters are interchangeable transports. The design test: the factory must survive any single vendor, app, or model disappearing.

Instead of auto-merge

A hard stop

The pipeline always halts at a local integration branch. Nothing is pushed, and nothing is merged into the branch you had checked out. You decide what happens next.

Survive any vendor

One factory, three interchangeable ways to do the work.

A worker lane is just a transport for one bounded turn. Any two lanes can stand in for the third, so no single provider's CLI or API is load-bearing. Every lane emits the same receipt schema, so the evidence trail is identical no matter who did the work.

Authentication stays where it already lives — a signed-in subscription CLI, a local endpoint that needs no key at all, or an adapter's own session. DevHarmonics never asks you for an API key.

The gate chain

Every consequential step can refuse — and a crashed gate is never a pass.

A change only reaches a local integration branch after clearing each gate in turn. Every refusal below is a real, distinct outcome the code returns, recorded in the receipt. Missing evidence always fails closed.

Evidence over confidence

A receipt for every attempt — including the ones that never start.

One schema across all three lanes records what was requested versus the model that actually resolved (never trusting a requested name as proof of what ran), the status, usage, a prompt hash, and the environment variables stripped before the worker touched anything.

resolutionVerified stays false unless the runtime itself reported its identity. Token counts are never invented as zero when a provider doesn't report them. The evidence is meant to be checkable, not taken on faith.

The credential boundary

Workers don't inherit your secrets.

Before a worker — or the check command that validates its work inside the same worktree — is spawned, DevHarmonics strips credential-shaped variables from its environment: named provider keys, cloud credentials, secret-bearing connection strings, and anything whose name carries a credential word.

worker environmentstripped
– ANTHROPIC_API_KEY   removed
– OPENAI_API_KEY      removed
– DATABASE_URL        removed
– DBPASSWORD          removed
+ PATH                 kept — resolution still works
+ SSH_AUTH_SOCK       kept — a socket, not a secret

A boundary, not a sandbox — it closes the ambient-inheritance path that would hand a worker every secret in your shell for free. The manual says so plainly rather than implying containment it doesn't provide.

How a run flows

From a natural-language task to a reviewed integration branch.

Intake

Point devharmonics run at a repository with a clean tracked working tree. It pins the current HEAD as the base and refuses to proceed on uncommitted tracked changes — nothing is stashed or silently skipped.

Isolated work

A worker on the lane you chose makes the change inside a throwaway worktree. The pipeline stages and commits it on a task branch; a no-op refuses immediately as worker-empty-diff.

Validate & gate

Your optional --check command runs in the worktree with a credential-stripped environment. Then the empty-diff and tampercheck gates run at the integration boundary — a crashed gate is never read as a pass.

Merge & review

A --no-ff merge into an integration branch, then an optional independent reviewer that judges the diff and receipts — never the worker's own story of what it did.

Stop for you

The run prints the integration branch and the evidence bundle, and stops. Bringing the change into your own history is a decision only you make.

The novel piece

Multi-repository integration sets

Plan a change that spans several repositories and judge it all-or-nothing. Each member is pinned to its own exact base commit at plan time, gets its own integration branch, and merges under the same per-repository lock. One task never touches two repositories — it's enforced structurally, not by convention — and advancement is genuinely two-phase: every member is gated and its merged candidate built first, with no branch moving; integration refs advance only after every member passes, so a refused member means nothing advances anywhere (set-blocked-not-advanced), never a half-applied set.

Admission, not routing

Qualification is a yes/no gate

Before a model is trusted with a role, it has to pass that role's harness — and a write role additionally requires a passing reasoning benchmark. It's an admission gate, deliberately: may this model do this job at all, appended to a ledger. There is no ranking engine, no cost-based routing, no "best model" heuristic to be gamed.

Where it fits

A pipeline and an evidence layer — not a cockpit, and not a raw agent.

DevHarmonics is scripts, gates, and receipts. It's meant to sit underneath a UI you already like and around the agents you already run, not to replace either.

Quick start

Install from source and probe your machine.

Requires Node.js 24+, Git, and tampercheck on your PATH — the integrity gate is a separate Python tool, deliberately not bundled, and without it a run refuses rather than integrating. There's no published package yet — install from source. npm ci pulls the single runtime dependency; npm link puts a global devharmonics on your PATH.

To make a change, add a lane and a repository — a signed-in claude/codex/agy, or a local Ollama / LM Studio server. doctor tells you, from real attempts, exactly what's reachable.

# 4 — make one gated change (--model is required for codex/claude)
$ devharmonics run \
    --repository ../my-project \
    --provider codex --model gpt-5.6-luna \
    --prompt "Add input validation to /signup" \
    --check "npm test" \
    --reviewer claude:sonnet \
    --require-evidence validator,review

Honest status

Early-stage, and specific about it.

DevHarmonics is functional and its full pipeline runs live against real tools, with CI on Windows and Linux. It is also new, installs from source, and carries limitations worth knowing before you rely on it. The project keeps that list in the open rather than smoothing it over.

In the spirit of the tool itself, its own gates were put through an adversarial falsification pass — a real command-injection, a symlink escape, and a credential-leak path were found against the code and closed, each with a regression test and a re-verification against a frozen build. That record is public, findings and fixes alike.
