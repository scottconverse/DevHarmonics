Local-first, host-agnostic, Apache-2.0

An agent makes the change. The gates decide if it lands.

DevHarmonics is a set of Node.js command-line scripts that let an AI coding agent make one bounded change to a git repository on your own machine. Every attempt writes a receipt, a failed gate refuses the change, and the run always stops before anything is pushed or merged into your branch.

The problem

When the only signal is "the model said it's done", a wrong answer looks like a right one.

A coding agent edits files, runs commands and reports success. DevHarmonics adds what that loop lacks: a boundary where the change is checked before it counts, evidence of what actually happened, and independence from any one vendor's app.

Instead of trust

Evidence

Every attempt writes a receipt, whether it succeeds, is refused, or never starts. An attempt that leaves no evidence is meant to be indistinguishable from one that never happened.

Instead of lock-in

Three lanes

Subscription CLIs, local model servers and ACP adapters are interchangeable transports. The stated design test: the factory must survive any single vendor, app or model disappearing.

Instead of auto-merge

A hard stop

The pipeline halts at a local integration branch. Nothing is pushed and nothing is merged into the branch you had checked out. What happens next is your decision.

Survive any vendor

One pipeline, three interchangeable ways to do the work.

A worker lane is a transport for one bounded turn. devharmonics run --lane subprocess|http|acp can drive any of them as the worker, and all three write the same receipt schema, so the evidence trail looks the same no matter who did the work.

Authentication stays where it already lives: a signed-in subscription CLI, a local endpoint that needs no key, or an ACP adapter's own session.

Subprocess
Supervised headless CLI
One bounded turn against a signed-in codex exec, claude -p or agy -p. The default lane.
auth: the CLI's own subscription sign-in
HTTP
Local model servers
One Anthropic Messages client, switched by base URL: Ollama and LM Studio by default, a LiteLLM proxy if you add one. The real Claude API is an explicit opt-in only.
auth: none for local endpoints
ACP
Agent Client Protocol
A live, multi-turn session over stdio with any ACP adapter on your PATH (default claude-code-acp). Permission requests are denied, or only file edits are granted.
auth: the adapter's own session

The gate chain

Every consequential step can refuse, and a crashed gate is never a pass.

This is the order devharmonics run applies them. Each refusal is a distinct reason the code returns and records in the evidence bundle. Missing evidence fails closed.

  1. STEP 01

    Isolated worktree

    The worker edits a fresh git worktree in your OS temp directory, never your checkout. A dirty tracked tree is refused at intake.

  2. STEP 02

    Worker output

    The pipeline commits what changed. Nothing staged earns one retry, then the run refuses.

    worker-empty-diff
  3. GATE 03

    Base ancestry

    The pinned base must be an ancestor of the worker branch, so a stale branch cannot sneak in ungated changes.

    stale-worker-base
  4. GATE 04

    Empty diff

    A branch that changed nothing does not pass, so a no-op never reads as green.

    empty-diff
  5. GATE 05

    tampercheck

    An integrity scan of the diff. The binary must first answer --version like a real tool, and its path and sha256 are recorded.

    tampercheck-findings, tampercheck-unavailable
  6. GATE 06

    Merged candidate

    A --no-ff merge is built detached, then scanned again, because the delivered tree is not the worker's tree.

    merge-conflict, final-artifact-findings
  7. STEP 07

    Your check

    Optional --check runs against that exact merged commit with a credential-stripped environment.

    validator-failed
  8. STEP 08

    Independent review

    Optional. The reviewer sees the diff and your check's result, never the worker's own account of what it did.

    review-not-ready, review-failed
  9. STOP: the owner-approval boundary. Only then does devharmonics/integration/<runId> advance. The run prints the branch and the evidence path and stops. Nothing is pushed.

Evidence over confidence

A receipt for every attempt, including the ones that never start.

One schema across all three lanes records the model you requested next to the model that actually resolved. A requested name is never treated as proof of what ran, so resolutionVerified stays false unless the runtime reported its own identity. Usage fields are null when a provider does not report them.

Integration adds its own bundle (integration.json) with every gate result and the tampercheck binary's path and checksum. A reviewer adds review.json. Each worker also writes a separate claims artifact that is compared against the real diff.

Assurance, derived from what passed

  • gates-onlydeterministic gates passed
  • validatedand your --check exited 0 on the merged candidate
  • reviewedan independent reviewer said READY
  • validated+reviewedboth

--require-evidence validator,review,claims refuses readiness when the evidence you demand is missing.

The credential boundary

Workers do not inherit your secrets.

Before a subprocess or ACP worker is spawned, DevHarmonics strips credential-shaped variables from its environment: named provider keys, cloud credentials, connection-string URLs, and any name containing a credential word. The same stripping applies to your --check command and to tampercheck, because both run inside the worktree the worker just wrote to.

worker environmentexamples from the manual
- ANTHROPIC_API_KEY   removed
- OPENAI_API_KEY      removed
- DATABASE_URL        removed
- DBPASSWORD          removed (name contains PASSWORD)
+ PATH                 kept, so commands still resolve
+ SSH_AUTH_SOCK       kept, a socket path, not a secret

A boundary, not a sandbox. It closes the ambient-inheritance path; it does not stop a worker with real file access from reading credentials off disk. The manual says so plainly.

How a run flows

From a prompt to a reviewed integration branch.

  1. Intake

    Point devharmonics run at a repository. It refuses tracked uncommitted changes (nothing is stashed), pins the current HEAD as the base, and keeps .devharmonics/ out of git through the private .git/info/exclude.

  2. Isolated work

    A worker on the lane you chose makes the change in a throwaway worktree on a devharmonics/task/<runId> branch. The HTTP lane is stricter: it may only touch the files you list with --files, and it commits only if your check passes.

  3. Gate

    Ancestry, empty-diff and tampercheck run on the worker's commits. A merge candidate is built without moving any branch, scanned again, and your check runs against it.

  4. Review and finalize

    With --reviewer or an evidence floor, the candidate is parked on a temporary ref and the owner-facing branch stays unchanged until a valid READY and every demanded item are in.

  5. Stop for you

    The run prints the integration branch and the evidence path, and stops. Bringing the change into your history is a decision only you make.

Guardrails with numbers

Spend and spawn limits that refuse before anything runs.

The documented design incident behind these was 255 agents and over 300 million tokens in about 45 minutes. Subprocess and ACP workers, reviewers and qualification harnesses all pass an admission gate before they spawn.

Fan-out ceilings

Workers and tokens

Defaults per state root over a rolling 24 hours: maxWorkers 100, maxConcurrentWorkers 3, maxTotalTokens 50,000,000. There is no off switch, only deliberately raised limits.

Paid lane

Double opt-in

A credentialed endpoint is refused unless budgets.allowPaidApi is true and maxPaidTokens is set. Dollar ceilings use real reported cost only, never a price table.

Per-run cap

--max-budget-usd

Forwarded to claude's own flag. Live-fire testing showed it is an overage stop, not a pre-flight guarantee, and the manual says so.

The novel piece

Multi-repository integration sets

Plan one change across several repositories and judge it all-or-nothing. Each member is pinned to its own base commit at plan time and gets its own integration branch. One task never touches two repositories, enforced structurally.

Advancement is two-phase: every member is gated and its candidate built with no branch moving, and only after all pass do the refs advance. If one is refused, nothing advances anywhere (set-blocked-not-advanced). devharmonics set integrates existing worker branches; it does not run workers itself.

Admission, not routing

Qualification is a yes or no

devharmonics qualify runs a real harness per role and appends the result, pass or fail, to a ledger. A write role additionally requires a passing reasoning benchmark, so a model that has never shown it reasons correctly does not get to edit unsupervised.

It answers whether a model may do a job at all. There is no ranking engine and no cost-based routing. devharmonics onboard goes the other way: it installs a pinned tampercheck CI workflow in a target repository, so the gate still holds if DevHarmonics is bypassed.

  • doctorProbe CLIs, endpoints, sign-in state and tampercheck.
  • runThe full gated single-repository pipeline.
  • setIntegrate existing branches across repositories, all-or-nothing.
  • onboardInstall repo-side enforcement (dry run by default).
  • qualifyAdmission sweep for models and CLIs (dry run by default).
  • worker / acpOne bounded attempt on the subprocess or ACP lane.
  • configShow the effective configuration and its source.
  • credentialStore API keys encrypted with Windows DPAPI (Windows only).
  • ledgerInspect and repair the spend ledger without ever resetting totals silently.

Tried against real tools

Tests prove the engine. Live-fire runs prove the boundaries.

Quick start

Install from source and probe your machine.

You need Node.js 24+, Git and tampercheck on your PATH. The integrity gate is a separate Python tool and is deliberately not bundled. Without it, run and set refuse with tampercheck-unavailable instead of integrating.

There is no published package yet. doctor reports, from real attempts, which lanes are reachable. To make a change you also need a signed-in codex, claude or agy, a local Ollama or LM Studio server, or an ACP adapter. Without npm link, run node scripts/cli.mjs <command> from the repository root.

    --prompt "Add input validation to /signup" \
    --check "npm test" \
    --reviewer claude:sonnet \
    --require-evidence validator,review

Honest status

Version 0.1.0, installed from source, specific about its limits.

The README records all eight spec slices as implemented and live-fire accepted on 2026-08-05, with CI on Windows and Ubuntu. It is also new, has no published package, and keeps a Known Limitations section that is meant to be read before you trust it with something that matters.

A repair pass on 2026-08-12 closed reviewer, claims and admission defects. That record also notes that some existing ACP timing tests had timed out at baseline, and it does not claim those as fixed.

Known limitations ↗
Built

Three lanes, qualification, the single-repository pipeline, review, and multi-repository sets are implemented.

From source

No npm or registry release. Install with git clone, npm ci and optionally npm link.

Partial

Metering depends on what providers report. agy reports no token usage, a resolved model from ACP is usually null, and HTTP-lane calls are not counted against the worker ceilings.

Partial

tampercheck covers Python and JavaScript/TypeScript patterns only. Rust patterns are a named, unbuilt gap.

By design

No resume, no automatic conflict repair, no dashboard, no ranking engine. An interrupted run starts over. Emdash is named as the intended human cockpit, as a companion and not a dependency.
